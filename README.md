# CHASSIS · Scenario Author

**Closed-loop Hypothesis-driven Agentic Scenario Synthesis for Intelligent Systems**

Перевод текстового описания тестового сценария в структурированный язык (DSL) для тестирования планировщиков движения автономного транспорта с помощью больших языковых моделей.

---

## О проекте

CHASSIS — модульная платформа для валидации планировщиков движения в симуляции. Этот репозиторий содержит один её модуль:

**Scenario Author** — переводит описание сценария на естественном языке в формальное описание на промежуточном языке CHASSIS DSL. Результат — **параметризованное семейство сценариев**: участники, их роли, манёвры, триггеры взаимодействий, диапазоны параметров и ограничения между ними. Описание проверено на корректность и пригодно для автоматической обработки следующими модулями.

Модуль решает одну задачу и не зависит от симулятора: на выходе у него только DSL. Привязка к конкретной карте, сэмплирование конкретных сценариев, конвертация в форматы симуляторов (CommonRoad, ASAM OpenSCENARIO) и оценка реалистичности выполняются другими модулями CHASSIS.

```
  текст ──► [ Scenario Author ] ──► CHASSIS DSL ──► привязка к карте ──► сэмплирование ──► симулятор
            (этот репозиторий)                      (другие модули CHASSIS)
```

## Какую проблему решаем

1. **Ручное создание сценариев.** Один качественный сценарий, созданный в редакторе сценариев, требует часов работы инженера. Набор тестов растёт медленнее, чем расширяется область эксплуатации (ODD).
2. **Невозможность автоматизации.** Пока сценарий существует только в голове инженера или в виде текста, его нельзя встроить в автоматическую цепочку генерации и проверки гипотез о слабостях планировщика. Нужен надёжный машиночитаемый перевод «текст → формальное описание», который можно вызывать как из интерфейса инженера, так и из других агентов.

**Целевая аудитория:** инженеры по созданию тестовых сценариев и инженеры в командах, разрабатывающих планировщик автономного транспорта.

## Архитектура

```
                    Запрос инженера
                          │
                          ▼
  ┌─────────────────────────────────────────────────┐
  │  1. Разбор запроса (LLM)                        │
  │     текст → структурированное намерение         │
  │     участники, роли, манёвры, взаимодействия    │
  ├─────────────────────────────────────────────────┤
  │  2. Построение семейства (LLM + правила)        │
  │     качественные формулировки → диапазоны       │
  │     параметров, триггеры, ограничения           │
  ├─────────────────────────────────────────────────┤
  │  3. Многоуровневая валидация (детерминированно) │
  │     • синтаксис: соответствие схеме DSL         │
  │     • ссылочная целостность: роли, триггеры,    │
  │       ограничения ссылаются на существующих     │
  │       участников                                │
  │     • физическая допустимость диапазонов        │
  │     • логическая согласованность триггеров      │
  ├─────────────────────────────────────────────────┤
  │  4. Исправление по ошибкам (LLM, ≤ N итераций)  │
  └────────────────────────┬────────────────────────┘
                           │
                           ▼
              семейство сценариев на CHASSIS DSL
              + список допущений и источников
```

### Ключевые принципы

- **LLM не генерирует геометрию.** Модуль описывает сценарий на уровне семантики (кто, где, что делает, при каком условии). Конкретные полосы, координаты и траектории не входят в DSL и строятся детерминированными инструментами следующих модулей. Это структурно исключает галлюцинации вроде несуществующих полос или кинематически невозможных траекторий.
- **Семейство, а не один сценарий.** Размытые формулировки («быстро», «внезапно», «плотный трафик») переводятся в диапазоны параметров, а не в одно произвольное число.
- **Явные допущения.** Всё, что в запросе не указано и было заполнено по умолчанию, записывается в отдельное поле `assumptions`. Инженер видит, что модель додумала, а не получает молча «дорисованный» сценарий.
- **Прослеживаемость.** Каждый атрибут связан с фрагментом исходного текста, из которого он получен, либо помечен как допущение.
- **Детерминированная валидация.** Все выходы LLM проходят проверку по схеме и правилам. Невалидный результат возвращается модели с конкретным сообщением об ошибке.
- **Не-LLM baseline.** Шаблонный разборщик на правилах служит запасным вариантом и базовой линией для сравнения.

## Технические вызовы

- **Неполнота запросов.** Инженеры описывают сценарий кратко и опускают «очевидное». Нужно разумно заполнять пропуски и явно помечать их.
- **Перевод качественных формулировок в числа.** «Пешеход внезапно выходит» должно стать согласованным диапазоном TTC и скорости, причём воспроизводимо для одинаковых формулировок.
- **Композиционные сценарии.** Несколько участников с согласованными по времени триггерами («когда эго поравняется с автобусом, из-за него выходит пешеход, а встречная машина начинает обгон»).
- **Галлюцинации атрибутов.** LLM склонны добавлять правдоподобные, но не запрошенные детали (погоду, участников, теги).
- **Устойчивость к перефразированию.** Разные формулировки одного сценария должны давать эквивалентные описания.
- **Работа на локальных моделях.** Данные компаний конфиденциальны, поэтому модуль должен работать на открытых моделях без внешних API.

## Формат данных: CHASSIS DSL

Пример семейства (упрощённо):

```json
{
  "id": "fam-occluded-pedestrian-001",
  "dsl_version": "0.1",
  "source": {"type": "text",
             "text": "Пешеход торопливо выходит из-за припаркованного фургона на двухполосной улице"},
  "environment": {"road": {"lanes": 2, "junction": "none", "parking": "roadside"}},
  "actors": [
    {"id": "ego", "role": "ego", "speed_kmh": [30, 60]},
    {"id": "van", "role": "occluder", "type": "van", "state": "parked",
     "placement": {"relative_to": "ego_lane", "side": "right"}},
    {"id": "ped", "role": "pedestrian", "persona": "hurrying",
     "maneuver": "cross_road",
     "start": {"behind": "van", "relative_to": "ego"},
     "trigger": {"type": "ttc_to_ego", "value_s": [1.5, 3.5]},
     "speed_mps": [1.5, 2.5]}
  ],
  "expected_interaction": "пешеход появляется из зоны окклюзии перед эго",
  "assumptions": [
    {"field": "actors.ego.speed_kmh", "value": [30, 60],
     "reason": "скорость не указана, типичный диапазон для городской улицы"},
    {"field": "actors.van.placement.side", "value": "right",
     "reason": "сторона парковки не указана, правостороннее движение"}
  ],
  "provenance": {
    "actors.ped.persona": "торопливо",
    "actors.van.type": "фургона",
    "environment.road.lanes": "двухполосной"
  }
}
```

Полная спецификация языка — в `docs/dsl-spec.md`.

## Использование (планируемый интерфейс)

Модуль доступен через CLI, Python API и MCP-сервер (для вызова из других агентов).

```bash
# Перевести описание в DSL
chassis-author translate "пешеход выходит из-за припаркованного фургона на двухполосной улице" \
    --model qwen3.6:35b --out families/fam-001.json

# Проверить готовое описание на соответствие схеме и правилам
chassis-author validate families/fam-001.json

# Пакетный перевод корпуса запросов
chassis-author translate-batch benchmark/queries/test.jsonl --out results/
```

```python
from chassis_author import ScenarioAuthor

author = ScenarioAuthor(llm="qwen3.6:35b", max_repair_iterations=3)
result = author.translate("пешеход выходит из-за припаркованного фургона")

if result.is_valid:
    family = result.family          # объект CHASSIS DSL
    print(family.assumptions)       # что модель додумала
else:
    print(result.errors)            # почему не удалось
```

## Оценка качества

Качество оценивается на корпусе запросов с эталонными DSL-описаниями, размеченными вручную.

| Метрика | Как измеряется | Цель |
|---|---|---|
| Синтаксическая валидность | доля выходов, соответствующих схеме DSL | ≥ 99% после исправления |
| Семантическая согласованность | доля выходов, прошедших все проверки ссылочной целостности и логики триггеров | ≥ 95% |
| Соответствие запросу | точность и полнота атрибутов относительно эталона, отдельно для окружения, участников, манёвров, взаимодействий | F1 ≥ 0,9; по взаимодействиям ≥ 0,85 |
| Галлюцинации | доля атрибутов, которых нет в запросе и которые не помечены как допущения | ≤ 3% |
| Корректность допущений | доля допущений, признанных экспертами разумными | ≥ 90% |
| Устойчивость к перефразированию | доля пар перефразировок, давших эквивалентные описания | ≥ 85% |
| Эффективность исправления | доля изначально невалидных выходов, исправленных за ≤ N итераций, и среднее число итераций | ≥ 90% |
| Стоимость | время и токены на запрос, работа на локальной модели | ≤ 30 с на запрос на локальной модели |
| Трудозатраты | время инженера на создание описания сценария по сравнению с ручным | сокращение ≥ 5 раз |
| Пригодность для дальнейшей обработки | доля описаний, успешно преобразованных следующими модулями CHASSIS в исполнимые сценарии | ≥ 95% |

Целевые значения уточняются после замера baseline.

### Baseline

- **Шаблонный разборщик на правилах** (ключевые слова и шаблоны) — нижняя граница.
- **LLM без схемы** (zero-shot) — оценка вклада контекста.
- **Разбор намерения из PlannerForge** — ближайший аналог: переводит запрос в структурированное намерение с фиксированным набором полей (локация, классы дорог, плотность трафика, состав транспорта, длительность). Сравнение показывает, что даёт расширение до участников, манёвров и взаимодействий.
- **Подходы генерации Scenic-кода** (ChatScene, NL2Scenic, Chat2Scenic) — сравнение «промежуточный DSL против прямой генерации кода сценария».

### Абляции

- контекст схемы в промпте / + примеры / + пошаговое рассуждение;
- с циклом исправления и без него;
- свободная генерация против генерации с ограничением по грамматике (constrained decoding);
- открытые локальные модели против коммерческих API;
- reasoning-модели с внешним пошаговым рассуждением и без него.

## Данные

| Назначение | Источник |
|---|---|
| Текстовые описания сценариев | запросы инженеров, функциональные сценарии из стандартов и регламентов |
| Сценарии из правил | правила дорожного движения |
| Сценарии из реальных ДТП | [NHTSA CISS](https://www.nhtsa.gov/crash-data-systems/crash-investigation-sampling-system) |
| Эталонные описания | ручная разметка корпуса на CHASSIS DSL, перефразировки для проверки устойчивости |
| LLM | открытые модели, запускаемые локально; коммерческие API — как верхняя планка сравнения |

## Связанные работы

- **PlannerForge** — LLM-агенты для сценарного тестирования планировщиков (TUM, EMNLP 2026): [arXiv:2609.08965](https://arxiv.org/abs/2609.08965), [GitHub](https://github.com/TUM-AVS/PlannerForge). Ближайший аналог; разбирает запрос в намерение с фиксированным набором полей уровня карты и трафика.
- **Scenic** — язык описания сценариев; **ChatScene**, **NL2Scenic**, **Chat2Scenic** — генерация Scenic-кода с помощью LLM.
- **TARGET** — перевод правил дорожного движения в DSL с помощью LLM.
- **Text2Scenario**, **LCTGen** — генерация сценариев по текстовому описанию.
